1What we believe happened

A trusted integration key changed where we pay a vendor — five days before a payment run.

TallyBridge Connect’s long-lived sync keys (key-tb-07 → LedgerOne, tb-sync-svc → HelpDeskr) were used by a second actor alongside the genuine nightly sync: first from home-broadband addresses (9–12 Aug), then from TallyBridge’s own build server inside our private link (10.20.4.77 “tb-build-02”, 17 Aug–6 Sep). It hunted support tickets for secrets, used a storage key pasted into a ticket to read our vendor bank-detail and payment files, and exported the vendor and payment lists, deleting the jobs. On 3 Sep it changed vendor V-0412’s bank account through the API with no approval. The vendor’s account (E16) is contradicted by our records on every claim we can test.

3Uncertainty — and what resolves it

  1. Has money already gone to a changed account? → bank payment files for the 23 Aug and 8 Sep runs.
  2. Outsider or vendor insider on tb-build-02 — one actor or two? Off-link and build-host activity share keys and targets, not addresses. → TallyBridge build and VaultWorks logs (we have no audit right, E08 §9.1).
  3. Is the “rotated” key already compromised? → re-issue key-tb-07 ourselves, IP-restricted, and watch for any use of the old one.
  4. Were any of the 70 vendor-contact changes from 1 Sep tampered with? They would defeat call-back checks (E19). → compare with contacts in vendor contracts.
  5. Gaps we cannot close from this data: a look-alike “tallybridge-support” domain registered 19 Aug (E20-F), but we hold no mail logs; BlueVault’s clock skew is unmeasurable, so its times are ± minutes (order of events unaffected).

5The problem we chose

A third-party integration can change where we send money, and nothing checks that change against anything else: no second system confirms which host acted, the API path enforces no approval, and nobody watches. We chose it because it is the one failure here where money leaves irreversibly — and the next run is 8 Sep.

Before the run: hold V-0412 and restore ****4417 · revoke key-tb-07, tb-sync-svc, bvk-7f3a · reset a.kapoor’s password · verify V-0233.

6The obvious approach — and why not

Per-log SIEM/UEBA rules: new IP, impossible travel, off-hours, volume. We built and ran it on this evidence: it drowns in staff on dynamic home addresses, misses the storage theft and admin attempt, and never fires on the bank change — made inside the link, in the sync window, under the real client name.
