## 1. Reproduction steps

Measured on Windows 11, Python 3.13.7, pandas 2.3.2, numpy 2.4.2. No network access, GPU or database is needed. The engine only reads the evidence folder and writes to the output folder.

```powershell
# 1. get the code and install the two dependencies
git clone https://github.com/kanishk2707/crimeathon.git
cd crimeathon
python -m venv .venv
.venv\Scripts\activate            # Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt

# 2. the supplied E01-E20 files and context.json are already in evidence/

# 3. analyse the supplied evidence and score it against our labels
python -m doubleentry analyze evidence --out out/real --truth analysis/analyst_labels.json

# 4. optional: regenerate the labels from their written rules
python analysis/make_labels.py evidence analysis/analyst_labels.json

# 5. optional: the hidden-variation suite (6 attack variants x 3 seeds, ~1 minute)
python -m doubleentry evaluate --out eval --variants all --seeds 7,11,23

# 6. optional: rebuild this proof pack
python analysis/build_proof_pack.py evidence docs/tier3
```

**Expected result of step 3** (this run took 30.2 s for 109,428 normalised rows): the console prints the score block, then `50 alerts in 1 thread(s); 1 vendor(s) to hold.` `out/real/` then contains:

| File | What it holds |
|---|---|
| `report.html` | The full report (opens offline in any browser) |
| `briefs.md` | The four one-screen briefs: General Manager, Finance, Legal, IT security |
| `hold_list.csv` | Per-vendor HOLD / VERIFY decision, last-known-good bank value, call-back advice |
| `payment_changes_scored.csv` | Every bank-detail change with its score and reasons |
| `timeline.csv` | All alerts in time order |
| `findings.json` | Every finding with the exact evidence records it relies on |
| `vendor_claims_checked.csv` | Each vendor claim, verdict and the records that contradict it |
| `least_privilege_policy.json` | The learned policy and what it would have refused |

To check you are using the same inputs, compare SHA-256 hashes with `docs/tier3/input_manifest.csv`.

## 5. Errors, false positives, false alarms and missed detections

### On the supplied data (final run)

- **False alarms: 0** of 99,456 benign records. **Missed detections: 0** of 181 labelled attacker records.
- **Alerts and paging.** 50 alerts were raised; the daily alert budget paged 42 and left 8 in the report for the next day. None is lost.
- **Below-threshold items, reported but not alerted: 43.** 36 × ledger, 4 × passport, 1 × exfil, 1 × callback, 1 × leavers. They point at 145 records, 0 of which are in our attacker labels. The ledger items are the vendor's announced contact sync (sent to change control, not dismissed: it was never reviewed and it rewrote call-back numbers). The rest are governance gaps and the call-back warning. A strict reader may count them as noise; we list them so nothing is hidden.
- **Least-privilege policy cost.** Replayed on the second half of the evidence it would have refused 70 genuine requests (all of them the announced contact sync, which began after the learning period). It would have needed one change-control approval.

### Before calibration

The first run on the real evidence raised about 24 false alarms. We changed three rules, each based on a documented fact rather than a tuned threshold, then re-ran the synthetic suite to confirm nothing regressed:

| False alarm | Rule change and its basis |
|---|---|
| Blank BlueVault addresses counted against people | The case file says E05 drops addresses; people are now judged only on external addresses. Software keys still alert on a blank address. |
| The announced 1 Sep contact sync raised incidents | Behaviour announced in E16 item 7 / E20-C 3.6.0 goes to change control (via context.json), not to the incident queue. |
| A person viewing a ticket counted as the ticket-to-key chain | Only the credential's own use after the exposure links the chain. |

### Errors found and fixed during development

| Error | Effect | Fix |
|---|---|---|
| Two timestamp columns after a rename in the clock solver | Crash on alignment | DataFrame built explicitly |
| dd/mm dates in E02 read as mm/dd | Wrong day for every HelpDeskr event after the 12th | Day-first detection on slash dates |
| `user:` / `key:` prefixes on principals | One actor counted as two | Prefixes stripped before identity resolution |
| E04 `ip_restriction` stored as a boolean, not a list | Passport check misread the restriction | Boolean and list forms both accepted |
| Sandbox flows counted as witnesses for production calls | A build host's sandbox history made it look trusted | System names keep sandbox and staging distinct |
| Greedy read-to-write pairing in the ledger | One write absorbed many unrelated reads | Each read is credited to the nearest following write |
| Clock solver failed at large skews | No offset found above about 5 minutes | All-pairs cross-correlation with a required spike |
| Indicator gap counted staff on dynamic home addresses | Inflated 'unlisted address' count | Only addresses where vendor credentials were used are compared |

### Missed detections in testing

- **`inside_worker`** (the vendor's real sync host skims small pages through real sync endpoints inside the real session): recall 0.44-0.56. Skims inside the genuine session stay within the ledger's balance tolerance. Its bank edits are still caught.
- **The obvious approach on the supplied data** misses 47 attacker records: the whole BlueVault pivot and the administrator password attempt.
- **No other variant** missed a labelled record.

## 6. Known limitations

1. **Labels are ours.** The real-evidence score is measured against `analysis/analyst_labels.json`, our own conclusions from the manual investigation, after one calibration pass on the same data. It shows the engine reproduces our investigation; it is not an independent accuracy figure.
2. **A compromised host that stays inside the sync's own pattern** (`inside_worker`) is only half caught (recall 0.44-0.56). Its bank edits are still caught by the firewall, so the money is protected even where the data theft is not.
3. **A forged write that balances a theft.** An attacker who also writes the stolen records into the partner system balances the ledger. The witness and grammar checks still apply.
4. **BlueVault clock skew could not be measured on the real data** (no events occur on both systems from one address). BlueVault times are shown uncorrected; the order of events, which are days apart, is unaffected.
5. **Approval references are checked for form and sequence, not existence.** Without an approval register (`approval_refs` in context.json) a forged but well-formed reference cannot be proven false.
6. **PDF and spreadsheet evidence is read by people.** Facts from E06, E13, E16 and E20 are typed into `evidence/context.json` with a citation for each. Without that file the billing, chain, claim and change-control checks switch off and the contact sync is reported as anomalous.
7. **The synthetic worlds are ours.** Perfect scores there prove the mechanisms work on attacks we designed, not on attacks we did not imagine.
8. **Batch, not live.** The engine analyses exported logs; blocking a change before it commits (slide 10 of Tier 2) is a next step, not built.
9. **Tested on Windows 11 with Python 3.13.** The code uses only pandas and numpy and no OS-specific calls, but Linux and macOS were not tested.
